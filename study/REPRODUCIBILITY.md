# Reproducibility and Environment Record

## Status and scope

This document separates four claims that are often collapsed:

1. **artifact integrity** — saved files match their recorded byte hashes;
2. **computational reproduction** — the locked code recomputes the same declared metrics;
3. **scientific replication/robustness** — a separate design or implementation supports the
   result; and
4. **generalization** — evidence applies to real events, instruments, or populations.

Ghostlight has local evidence for the first two in recorded environments. It has not
established the third or fourth. The container and CI files added with this record are
unexecuted templates, not retrospective evidence.

## Verification without experiment regeneration

From an already synchronized project root:

```bash
export MPLCONFIGDIR="$PWD/.mplconfig"
export PYTHONDONTWRITEBYTECODE=1
.venv/bin/pytest
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/ghostlight verify --project-root . --recompute
```

`verify --recompute` deterministically rebuilds and compares the machine-readable metrics
under the fixed specification. It is not an independent scientific replication and does
not establish real-world validity.

## Locked setup in a disposable directory

The following is the intended clean-room sequence once the project is attached to an exact
committed revision:

```bash
uv sync --frozen --extra dev --python 3.12 --no-editable
export MPLCONFIGDIR="$PWD/.mplconfig"
export PYTHONDONTWRITEBYTECODE=1
.venv/bin/pytest
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/ghostlight verify --project-root . --recompute
```

The command refuses lockfile updates but uses versions present in `uv.lock`; it does not
make the base operating system or BLAS immutable.

## Container template

[`Dockerfile`](Dockerfile) builds a Linux/Python 3.12 environment from an `uv` image tag,
installs the locked development environment non-editably, and runs tests, lint, format
checks, and deterministic verification during the build. The default container command
repeats verification.

The image tag is versioned but not digest-pinned. Before release:

1. resolve and record the exact base-image digest;
2. build from the exact reviewed commit;
3. record Docker/BuildKit version, target platform, image digest, and build log;
4. run the image on a clean host; and
5. attach an SBOM and provenance attestation where the hosting platform permits.

No image has been built, pushed, or published by adding this template.

## Continuous-integration template

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) is a least-privilege template with
commit-pinned actions. Because this local project has no valid committed `HEAD` or configured
remote, the workflow has not run and cannot supply a status badge or release gate. If
Ghostlight remains a subdirectory of an umbrella repository, the workflow must be moved to
the umbrella repository's root `.github/workflows/` and its working directory adjusted.

## Full experiment regeneration

Full stochastic regeneration is a materially different operation from verification. It
rewrites the saved tables, figures, metrics, narrative result, and manifest. Do not perform
it as a casual environment check. A regenerated study must:

- preserve the current candidate as a recoverable evidence snapshot;
- use an approved protocol and new release identity;
- write to a new output location until reviewed;
- compare old and new specification, environment, and artifacts explicitly; and
- obtain owner scientific/copy authorization before replacing public claims.

The prospective [ROBUSTNESS_PROTOCOL.md](ROBUSTNESS_PROTOCOL.md) and
[REAL_DATA_EXTENSION_PROTOCOL.md](REAL_DATA_EXTENSION_PROTOCOL.md) define new evidence
tracks; neither may be backfilled into the frozen run.
